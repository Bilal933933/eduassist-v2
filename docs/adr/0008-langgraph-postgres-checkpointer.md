# ADR-0008: اعتماد حافظ PostgreSQL لحالة لانغ غراف

## الحالة
معتمد

## السياق
يحتاج الرسم إلى الاحتفاظ بالحالة بعد إعادة تشغيل الخادم، بينما يحفظ الحافظ الحالي البيانات داخل ذاكرة العملية فقط.

## القرار
- يستخدم التطبيق `AsyncPostgresSaver` من الحزمة الرسمية `langgraph-checkpoint-postgres`.
- ينشئ أمر إعداد مستقل جداول الحافظ مرة واحدة، ولا تُنشأ الجداول عند كل تشغيل للتطبيق.
- تنشئ نقطة دخول التطبيق اتصال الحافظ وتحقنه في الرسم طوال دورة حياة الخادم.
- لا تنفذ راوتات فاستAPI (FastAPI) استعلامات قاعدة بيانات مباشرة.
- تُعزل نقاط التفتيش بمفتاح مركب من معرّف المستخدم ومعرّف المحادثة داخل `thread_id`.
- جداول الحافظ داخلية ومدارة بالكامل بواسطة لانغ غراف، ولذلك لا نعدّل مخططها لإضافة `user_id`؛ يتحقق عزل المستخدم في المفتاح المركب.

## البدائل المدروسة
- `InMemorySaver`: مناسب للاختبارات فقط لأن الحالة تضيع عند إعادة التشغيل.
- تعديل جداول الحافظ الرسمية: مرفوض لأنه يكسر ترحيلات الحزمة وتوافقها.
- حفظ الحالة يدويًا: مرفوض لأنه يكرر مسؤولية لانغ غراف.

## النتائج
- إيجابيات: استمرارية الحالة مع أقل كود مخصص، وإمكانية استكمال المحادثة بعد إعادة التشغيل.
- سلبيات: جداول الحافظ لا تعرض `user_id` كعمود مستقل، ويجب استخدام دالة بناء إعداد نقطة التفتيش دائمًا.

## خطة الترحيل
تشغيل `python -m db.setup_checkpointer` مرة واحدة بعد تجهيز PostgreSQL، ثم تشغيل التطبيق بصورة طبيعية.
