# ADR-0006: تأسيس سيناريو الترحيب بأقل هيكل

## الحالة
معتمد

## السياق
نحتاج التحقق أولًا من تكامل فاستAPI (FastAPI) مع لانغ غراف (LangGraph) ونقطة التفتيش قبل إضافة النقل اللحظي أو بقية الطبقات.

## القرار
- تبدأ الواجهة الخلفية بملف للرسم، وملف للمسار داخل الواجهة البرمجية، ونقطة دخول، ومجلد إعدادات.
- تدخل رسالة المستخدم عبر HTTP وتخرج أحداث الرسم عبر مقبس الويب (WebSocket) وفق ADR-0007.
- يبقى تنفيذ الاتصال داخل ملف الواجهة البرمجية ما دام هناك سيناريو واحد، ويُنقل إلى طبقة مستقلة عند ظهور حاجة فعلية.
- تضاف المجلدات والطبقات عند وجود حاجة فعلية فقط.

## النتائج
- إيجابيات: بداية قابلة للفهم والاختبار بلا تجريد مبكر.
- سلبيات: سجل الاتصالات داخل ذاكرة عملية واحدة ولا يدعم تعدد الخوادم.

## بوابة التقييم
- سيناريو الترحيب حتمي ولا يستخدم استرجاعًا أو نموذج لغة كبيرًا، لذلك لا ينطبق عليه استدعاء@10 (Recall@10) أو مقياس الأمانة (Faithfulness).
- بوابة القبول الحالية هي نجاح اختبارات العقدة، وعزل نقطة التفتيش، ومسار الواجهة البرمجية.
- تصبح المقاييس الملزمة قابلة للتطبيق عند إضافة أول مسار للاسترجاع أو التوليد، ولا يجوز عندها دمج التغيير قبل تسجيل النتائج في `evaluation/results/`.

## خطة الترحيل
عند تعدد سيناريوهات الأحداث، تُستخرج إدارة الاتصال إلى طبقة نقل مستقلة دون تغيير الرسم.
